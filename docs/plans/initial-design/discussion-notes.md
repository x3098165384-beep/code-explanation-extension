## 背景与已知事实

### 用户实际需要的讲解

用户认可的是顺着真实代码翻译：先说明 `CurrentPoint` 是本 NPC 当前占用的点位，`sceneManager` 是场景点位管理器，`this` 是当前 NPC，再把 `!= null`、`&&`、`!IsCurrentPointAvailable(this)` 连成完整中文条件，随后解释调用发生什么。只给整段业务总结不满足这个需要。

讲解 diff 时还需要明确改前、改后和原因，但不要求每步都套固定栏目。此前导览的宽表格和大量重复分段在评论框中难读；后来改成列表，用户仍认为 CodeTour 不适合当前 diff 阅读体验。现有任务背景和最终逐句解释偏好见[杜兰特任务交接](../../../../../svnVO/trunk/Vonimir/docs/handoff/2026-10-20-145522-durant-npc-fix-and-code-explanation.md)。

### CodeTour 可以 fork

已核对安装版 0.0.61 的 `package.json`、`LICENSE.txt`，以及上游 [MIT 许可证](https://github.com/microsoft/codetour/blob/main/LICENSE.txt)：允许修改和分发，使用其代码时须保留相应版权及许可声明。上游为 [microsoft/codetour](https://github.com/microsoft/codetour)。本轮没有创建远程 fork 或本地插件项目。

### 已支持 Markdown，现有显示受评论框限制

安装版源码映射的 `src/player/index.ts` 中，`CodeTourComment` 使用 `new MarkdownString(body, true)`，并设置 `supportHtml = true`；通过 `comments.createCommentController` 和 `createCommentThread` 在代码旁显示。它没有把讲解当作只能显示的纯文本。

因此用户提出的“不支持 md 渲染”应记录为当前呈现效果不满意，不能据此把新增 Markdown 解析器当成必要工作。截图中已有表格和粗体渲染，问题包含内容过长、表格难辨及部分粗体写法。排版和文字生成方式需要分别改进。

[VS Code MarkdownString 文档](https://code.visualstudio.com/api/references/vscode-api#MarkdownString)说明支持 Markdown 和有限 HTML。沿用原生评论框时，不能承诺通过 fork CodeTour 就能完全自定义字体、表格、宽度或网页布局。公开的 [Webview 文档](https://code.visualstudio.com/api/extension-guides/webview)提供自定义 HTML/CSS 界面，但其公开承载位置包括独立编辑页、侧栏或面板，不能直接把它当作原生代码行内评论框的替换接口。

### diff 需要明确改前和改后的定位

已核对安装版 `schema.json`、源码映射中的 `src/utils.ts:getStepFileUri` 和 `src/player/index.ts:showDocument`：现有步骤有 `file`、`uri`、`line`、`pattern` 等字段，读取时也处理 Git `ref`。显示时优先找同 URI 的可见编辑器，否则调用 `showTextDocument`。因此它并非完全不能读取 Git 历史内容，但当前步骤没有专门表达 diff 两侧及两边行号的一组字段，不能据此保证用户需要的 diff 导览。

[TabInputTextDiff](https://code.visualstudio.com/api/references/vscode-api#TabInputTextDiff) 提供改前与改后两个资源 URI；[CommentController](https://code.visualstudio.com/api/references/vscode-api#CommentController) 允许按资源 URI 和代码范围创建评论。推断可以用这些接口研究在正确一侧挂讲解并保持 diff，但本轮没有实际验证。应先验证改前删除行、改后新增行和跨步骤跳转，不能只验证普通文件就宣称 diff 已支持。

### 只读讲解与现有附加功能

安装版 `src/player/index.ts:generatePreviewContent` 会给围栏代码块追加 Insert Code 操作，还支持说明中的部分命令转换。请求者看重的是不改变源码的阅读体验，这些功能不是当前目标。若保留代码块，提案是让它们仅用于展示；这不是对现有插件或配置的修改授权。

## 已确认的决定

- 需要不写入源码的行内讲解，并按顺序浏览。
- 需要围绕实际代码修改阅读，当前 CodeTour 的 diff 体验不满足需求。
- 喜欢代码名称与实际业务对象逐一对应、顺着条件和调用翻译的自然讲解。不能仅靠抽象概括替代。
- 现有大表格和生硬重复模板的呈现不满意。改前、改后仍有价值，显示方式不能妨碍阅读。
- 路线选择：请求者明确提出新开独立小项目自己实现，不继续沿用先 fork CodeTour 的建议。只需要行内讲解和顺序浏览这两个核心特点，不以复刻 CodeTour 全部功能为目标。

项目目录已按请求单独建立。首版具体范围、实现细节和交付时间尚未约定，不能把下方建议记为已经接受或已经完成。

## 待讨论的方案

### 只做阅读的小型独立插件

路线已选择独立项目。建议首版只负责读取和显示讲解：加载独立讲解文件，定位实际代码或 diff，一次显示当前讲解，提供上一步、下一步和步骤选择。无需复刻录制、终端操作或代码插入等当前不需要的功能。可考虑读取现有 `.tour`，但兼容格式尚未决定。

独立实现可以围绕 diff 明确保存版本和左右位置，减少无关功能；代价是要自己完成定位、导航、窗口切换后的恢复及关闭时的清理。同样使用原生评论框时，也同样受其显示限制。若需要网页级版式，则需另行判断显示在独立阅读页还是继续坚持原生 diff 内的行内位置，不能把两者说成同一种界面。

建议首版先覆盖普通文件和一组固定版本的 diff，用少量真实讲解验收：改前的删除行、改后的新增行均显示在正确位置；点击下一步保持对应 diff 并跳到正确代码；结束讲解后评论移除，源码内容和 Git 差异不变。核心播放功能不需要先接入模型或设计录制界面。

插件项目已独立于 Unity 工程，当前讨论记录也已迁入本项目。后续插件代码在当前项目中开发，Vonimir 中仅保留原记录的迁移链接。

### 讲解方式和显示工具分别处理

无论最终采用哪种插件，内容保持自由文字，不强制每步都有“情境／改前／改后／原因”。生成讲解时以逐句翻译为主，需要解释修改时再补改前、改后和理由；完整执行例子用于真正需要展示变量变化的位置。

这需要后续调整讲解技能或生成约定，插件不必内置模型调用才能显示这种文字。本轮只记录方向，尚未修改现有技能或导览。
