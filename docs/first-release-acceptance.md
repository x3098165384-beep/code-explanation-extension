## 改变 HEAD 的最后一项

第 24 项会主动改变演示仓库的 HEAD，因此放在普通阅读、停止和第 26 项内容保持检查之后。不要在插件项目仓库执行，不要用普通提交把已经暂存的演示修改收进去。

下面的命令明确指向上文的独立 `project`，可在确认路径后手动执行：

```powershell
git -C 'F:/Sync/MyProjects/code-explanation-extension/.scratch/first-release/runtime/acceptance/project' -c user.name=XGH -c user.email=xgh@example.invalid -c commit.gpgsign=false -c core.hooksPath='F:/Sync/MyProjects/code-explanation-extension/.scratch/first-release/runtime/acceptance/empty-hooks' commit --allow-empty --only -m '验收：更新演示提交基准'
```

此命令仅用于主动制造新的提交基准。执行前先记录旧 HEAD 和暂存区，执行后核对只有 HEAD 按预期变化，原已暂存和未暂存示例仍在。`lecture-disk.md` 和 `lecture-unsaved.md` 都记录旧 HEAD；因此之后的第 6 步失效是本项预期，不要通过重跑准备工具覆盖当前验收工程。

## 建议分批保留的截图

每项都需文字结果；已有同一个界面的清晰截图可以同时支持多个编号，不要求机械地为 26 项各截一张。正式插件首次验收建议分下面六批执行，先观察再记录，出现失败时保留当时界面。

1. **正常讲解与历史比较：** 实际查看第 1 步长正文，并在第 3–5 步之间往返；最少保存第 3 步左侧正文、第 5 步双侧高亮两张。对应 1–5、22、25。普通 Markdown 的既有显示接口证据可引用任务 01，但仍需实际观察正式讲解的全部正文；若布局或末尾可达性有变化，追加截图。
2. **未保存内容及整个新增、删除文件：** 实际查看第 6–8 步，最少保存未保存讲解第 6 步一张，证明正式读取的当前内容同时包含三项修改。对应 6、7、13；整个新增和删除的观察补文字结果，界面异常时截图。后台另核对磁盘和暂存区。
3. **代码变化与失效正文：** 保存一次唯一重新定位，以及一次多匹配或目标改变后的错误与 Markdown 正文。对应 8–12、14，其余变体仍逐项补文字结果。
4. **自动更新与恢复：** 最少保存重排后仍停在同一步的界面、讲解损坏且代码也不对应时的只读“上一次成功加载的讲解”两张。对应 15–19，修复保存后的正常显示及文件错误解除补文字结果，恢复失败时追加截图。
5. **最后一步、停止和主动恢复：** 保存停止后的界面与随后主动重开的进度。对应 20、21、23、26；重启后未主动打开时是否保持无讲解，以文字记录，异常时截图。
6. **HEAD 改变：** 最少保存第 6 步的基准错误一张，再实际查看第 3–5 步中的一个固定历史步骤并补文字结果。对应 24，再核对暂存区与源码未被插件改变。

这六批建议最少保留 10 张正式截图；截图不是每项实际操作的替代，也不是通过结论。截图路径和实际结果随请求者操作逐项填写。连续保存、快速切换、替换讲解及停止后的迟到成功或失败，还需结合项目的可控读取顺序自动检查；多次手动点击未遇到错误不足以替代这些检查。
