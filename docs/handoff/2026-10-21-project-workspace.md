## 当前任务

请求者希望将 VS Code 行内代码讲解插件作为独立小项目推进，并在这个项目的 Codex 工作区继续交流。原会话从 Vonimir 的 NPC 修复和代码讲解延伸而来；后续插件工作不应继续放在 Unity 工程中。

## 阅读顺序

1. [README](../../README.md)：项目目标和当前准备状态。
2. [最终讨论记录](../plans/initial-design/discussion-notes.md)：已确认目标、技术调查、尚未确认的方案及来源链接。这是产品讨论的现有记录，不在本文件重复。

## 已完成与尚未完成

项目目录及上述文档已经建立，原讨论记录已经迁入。尚未初始化 Git、配置项目自己的 AGENTS.md 和任务记录规则、创建扩展代码或安装依赖。尚无已接受的完整规格或开发任务。

准备本交接时，Codex 的已登记项目只有 codex 和 Vonimir，当前会话的工作目录仍是 Vonimir。可用工具没有登记任意本地项目或直接改变当前会话工作目录的接口，因此没有完成应用中的项目切换。应先将本目录加入 Codex 的独立本地项目，再从该项目继续。不能把文档迁移或命令的 workdir 参数当作会话工作区已经迁移。

## 继续时要保留的边界

- 用户已经结束 discuss，不自动重新启动讨论访谈。讨论记录中的建议不等于全部获得确认。
- 路线是独立实现；行内讲解不改源码、按顺序阅读是用户最看重的特点，实际 diff 阅读也是目标。
- 讲解应逐句说明代码名称的实际含义、条件和调用，再按需要说明改前、改后与原因。不要恢复宽表格或每步重复同一套栏目。
- CodeTour 本来支持 Markdown；原生评论框的显示限制和讲解文案问题要分别判断。尚未实际验证新的 diff 定位与显示方案。
- 不自动继承 Vonimir 的 Unity、资源、测试、文档路径等项目规则，也不继续修改游戏代码、旧导览或旧技能。

## 建议使用的技能

1. `setup-matt-pocock-skills`：先为当前小项目确定自己的任务记录、项目规则和领域文档约定。可提出本地 Markdown 任务记录和 AGENTS.md 的简短方案，不照搬 Unity 工程整份规则。
2. `git-repo-init`：确定要启用版本管理后，在本项目内初始化 Git；没有要求另存 Git 元数据或创建远程仓库。
3. `prototype`：先用真实的逐句讲解验证 diff 两侧定位、顺序跳转和显示效果，再据结果确定实现方式。
4. `to-spec`：据已确认目标和验证结果整理首版规格，保留尚未确定的事项；之后再决定拆任务和实现。

项目初始化和显示验证是建议的下一步，当前交接没有执行这些技能，也没有把任何技术方案当作已验证结果。
